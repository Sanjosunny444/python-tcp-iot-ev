========================================================================
DEVICE SIDE (DiLu protocol — what the CCU holds)
========================================================================

--- Query / Setting parameter (CMD 0x10 / 0x11) ---

  Field                      | What it controls
  ---------------------------|-------------------------------------------
  APN / Username / Password  | Cellular network login
  BLE name                   | BLE advertising name
  Heartbeat interval (1B)    | Device -> server keepalive rate (minutes)
  Unlock notify interval (4B)| Status upload rate when unlocked (seconds)
  Lock notify interval (4B)  | Status upload rate when locked (seconds)
  Static automatic lock (4B) | Auto-lock after inactivity (seconds)
  Vibration sensitivity (1B) | Motion / alarm sensitivity
  Alarm tone times (1B)      | How many times alarm sound plays
  Chain lock BLE MAC / KEY   | BLE pairing for chain lock
  Battery lock BLE MAC / KEY | BLE pairing for battery lock


--- Scooter / ride settings (S7 / S4 equivalent inside device) ---

  Headlight, speed mode, throttle, cruise, startup behavior,
  speed limits, etc.


--- Version info (CMD 0x06 Get version response) ---

  Field                      | Size
  ---------------------------|--------
  CCU serial number          | String 32
  CCU firmware version       | String 32
  CCU hardware version       | String 32
  ECU serial number          | String 64
  ECU firmware version       | String 32
  ECU hardware version       | String 32
  Battery serial number      | String 64
  Battery firmware version   | String 32
  Battery hardware version   | String 32
  Battery information        | Byte 23
  CCU information            | Byte 16

  Omni field       | Value        | DiLu source             | Verified

------------------------------------------------------------------------
S5 — IOT Device Settings -> DiLu 0x11 Setting Parameters
------------------------------------------------------------------------
  Direction: Server -> Bridge -> Device
  Action:    Translate + echo S5 back to server

  Omni S5 field              | DiLu 0x11 field           | Conversion
  ---------------------------|--------------------------|--------------------
  Accelerometer (0-3)        | Vibration sensitivity    | 1->10, 2->6, 3->3
  S6 upload in unlock (1/2)  | Unlock notify interval   | 1->0, 2->keep/10
  Heartbeat interval (sec)   | Heartbeat interval (min) | sec / 60
  S6 interval in unlock (sec)| Unlock notify interval   | direct

  Fields not in S5 (APN, BLE keys, etc.) are sent as last-known values.


------------------------------------------------------------------------
S7 — Scooter Setting 1 -> DiLu 0x03 + 0x07
------------------------------------------------------------------------
  Direction: Server -> Bridge -> Device
  Action:    Translate + echo S7 back to server

  Omni S7 field          | DiLu CMD  | DiLu field         | Conversion
  -----------------------|-----------|--------------------|-----------------
  Headlight (1/2)        | 0x03      | Headlight control  | 1->0x00, 2->0x01
  Mode (1/2/3)           | 0x07      | Mode + Speed limit | 1,2->soft, 3->sport
  Throttle response (1/2)| -         | not in device doc  | -
  Taillights (1/2)       | -         | not in device doc  | -

  Mode -> Speed mapping:
    Omni 1 (low)    -> DiLu soft  (0x00) + Low speed limit
    Omni 2 (medium) -> DiLu soft  (0x00) + Medium speed limit
    Omni 3 (high)   -> DiLu sport (0x01) + High speed limit

------------------------------------------------------------------------
E0 — Fault Code Upload (auto-detected from status)
------------------------------------------------------------------------
  Direction: Bridge -> Server (auto, when fault code changes)
  Trigger:   Status notification with non-zero Fault code (different from last)
  Server:    Auto-acknowledges with *SCOS,OM,<IMEI>,E0#

  Omni E0 field    | Value  | DiLu source         | Verified
  -----------------|--------|--------------------|---------
  Error code       | 3      | Fault code (0x0003)| YES

  Format: *SCOR,OM,<IMEI>,E0,<error_code>#

  DiLu fault codes (Appendix 1, scooter):
    Bit0 = Overcurrent       Bit4 = Up-bridge fault
    Bit1 = Low voltage       Bit5 = Down-bridge fault
    Bit2 = Over voltage      Bit6 = Motor fault
    Bit3 = Motor stalling    Bit7 = ECU other faults
    Bit8 = Speed bar fault   Bit10 = ECU firmware fault
    Bit9 = Brake bar fault   Bit11 = CCU-ECU lost comm

  Behavior:
    - Fault appears (0 -> non-zero):  E0 sent + H0
    - Same fault repeats:             H0 only (no duplicate E0)
    - Fault clears (non-zero -> 0):   H0 only, flag reset
    - New fault appears:              E0 sent again


------------------------------------------------------------------------
R0 — Unlock/Lock Request (handshake)
------------------------------------------------------------------------
  Direction: Server -> Bridge (no device query)
  Action:    Bridge generates random KEY (0-255), stores it, echoes R0
             back to server with the KEY. DiLu doesn't need a handshake.

  Omni R0 server->lock args:
    [operation, key_time, user_id, timestamp]
    operation: 0=unlock, 1=lock, 2=RFID unlock, 3=RFID lock

  Omni R0 lock->server response:
    [operation, KEY, user_id, timestamp]

  Format: *SCOR,OM,<IMEI>,R0,<operation>,<KEY>,<user_id>,<timestamp>#

  Note: R0 must be sent before L0 or L1. The KEY from R0 response
  is required in the L0/L1 command for verification.


------------------------------------------------------------------------
L0 — Unlock Command -> DiLu 0x02 (motor unlock)
------------------------------------------------------------------------
  Direction: Server -> Bridge -> Device
  Action:    Verify R0 KEY, send DiLu 0x02 (unlock motor), forward
             result to server when device responds

  Omni L0 server->lock args: [KEY, user_id, timestamp]

  Omni L0 field      | DiLu 0x02 field       | Value
  -------------------|-----------------------|------------------
  KEY                | (verified by bridge)  | must match R0 KEY
  unlock action      | lock_control          | 0x01 (unlock)
  motor lock         | lock_type             | 0x00 (motor)

  Omni L0 lock->server response: [status, user_id, timestamp]
    status: 0=success, 1=failure, 2=KEY error

  Format: *SCOR,OM,<IMEI>,L0,<status>,<user_id>,<timestamp>#

  Per client: always use lock_type=0x00 (motor) for main ride lock.
  RFID unlock/lock uses same mapping as normal unlock/lock.


------------------------------------------------------------------------
L1 — Lock Command -> DiLu 0x02 (motor lock)
------------------------------------------------------------------------
  Direction: Server -> Bridge -> Device
  Action:    Verify R0 KEY, send DiLu 0x02 (lock motor), forward
             result to server when device responds

  Omni L1 server->lock args: [KEY]

  Omni L1 field      | DiLu 0x02 field       | Value
  -------------------|-----------------------|------------------
  KEY                | (verified by bridge)  | must match R0 KEY
  lock action        | lock_control          | 0x00 (lock)
  motor lock         | lock_type             | 0x00 (motor)

  Omni L1 lock->server response: [status, user_id, timestamp, cycling_time]
    status: 0=success, 1=failure, 2=KEY error
    cycling_time: ride duration in minutes

  Format: *SCOR,OM,<IMEI>,L1,<status>,<user_id>,<timestamp>,<cycling_time>#

========================================================================
MISMATCHED UPDATE PROTOCOL — NOT POSSIBLE TO TRANSLATE
========================================================================

  decision: OTA/firmware updates are excluded from the bridge.

  The Omni server and DiLu device use fundamentally different update
  methods that cannot be translated in real-time:

  Omni (U0/U1/U2): Sends firmware chunk-by-chunk over TCP (128 bytes
                    per round-trip). Server holds the file and sends
                    each piece on request.

  DiLu (0x08/0x0E/0x0F): Sends an FTP link to the device. The device
                          connects to the FTP server independently and
                          downloads the full file on its own.

  Omni commands excluded:
  -----------------------
  U0      | Detect upgrade / boot upgrade
  U1      | Get upgrade data (128-byte chunks)
  U2      | Upgrade success notification
  U5      | HTTP upgrade (partial IOT support)
  U6      | HTTP upgrade status

  DiLu commands excluded:
  -----------------------
  0x08    | CCU OTA (FTP download)
  0x0E    | ECU OTA (FTP download)
  0x0F    | Audio OTA (FTP download)


========================================================================
BLE COMMUNICATION — NOT POSSIBLE VIA BRIDGE
========================================================================

  The Omni App communicates with the IoT device directly via Bluetooth
  (BLE) for lock/unlock and scooter control. The bridge sits on the
  TCP path (server <-> device) and has no BLE connection.

  The App cannot control the DiLu device via BLE because they use
  different BLE protocols (Omni BLE vs DiLu BLE).

  All lock/unlock operations must go through the server (R0/L0/L1)
  which the bridge CAN translate. Direct App-to-device BLE control
  is not possible with this architecture.


========================================================================
AES-128-ECB ENCRYPTION (DiLu spec section 4.3)
========================================================================

  Status: IMPLEMENTED (aes_handler.py)
  Toggle: device_state["aes_enabled"] = True/False (hardcoded for now)

  Protocol:
    - Only content + CRC are encrypted (start code + length are plaintext)
    - Length field = content size BEFORE encryption
    - Encrypted block = content + CRC + random padding to multiple of 16
    - Algorithm: AES-128-ECB (standard, pycryptodome library)

  Key hierarchy:
    Root key (16B)    -> pre-configured per device, stored in device_state
    Session key (16B) -> generated by device, encrypted with root key,
                         sent in auth (CMD 0x04)

  Auth detection:
    Plaintext mode: root key field = raw password (matches known root key)
    Ciphertext mode: root key field = AES_encrypt(session_key, root_key)
    (Detection logic to be added later, currently hardcoded bool)

  Incoming packets (device -> bridge):
    1. Read 5155 + length (plaintext)
    2. Calculate encrypted block size: ceil((length + 2) / 16) * 16
    3. Read encrypted block
    4. Decrypt with session_key
    5. First [length] bytes = content, next 2 bytes = CRC
    6. Discard remaining padding
    7. Verify CRC, parse normally

  Outgoing packets (bridge -> device):
    1. Build content normally
    2. Calculate CRC on content
    3. Pad content + CRC to next multiple of 16 (random bytes)
    4. Encrypt with session_key
    5. Send 5155 + length (original content size) + encrypted block

  Test packets in test.py:
    x = [AES] Auth (encrypted session key inside)
    y = [AES] Encrypted Status Notification

  Verified: auth decrypts session key correctly, encrypted status
  decrypts and parses all fields correctly (CRC passes).
